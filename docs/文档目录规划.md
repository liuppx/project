# Project 文档目录规划

> 状态：当前有效
> 适用范围：仓库 `docs/` 下的人类可读工程文档
> 维护对象：开发、架构、产品、运维和集成文档

本文档是 `docs/` 的组织契约。它解决三个问题：新文档放在哪里、现有文档如何逐步迁移、怎样让文档随着代码迭代而保持可信。

本规划只定义 `docs/` 的工程文档，不把产品内 AI 检索知识库混入其中。`resources/ai-kb/` 有自己的目录、chunk 和校验规则；用户可见功能或 API 行为发生变化时，按本文档的同步规则判断是否同时更新两处内容。

## 一、设计原则

1. **按文档用途归类，不按团队或服务复制目录。** 同一主题只能有一个权威正文，跨系统内容通过链接引用。
2. **当前实现、提案、决策和历史必须可区分。** 读者不能把草案或旧方案误当成生产依据。
3. **文档和代码一起演进。** 接口、配置、部署、生成脚本发生变化时，在同一个变更中更新受影响文档。
4. **根目录只做入口。** 详细内容进入分类目录，`README.md` 只做索引，不复制正文。
5. **渐进迁移。** 先固定规则，再按主题迁移；不为了“整齐”一次性移动所有文件。
6. **可验证、可追责。** 每份当前文档都要有负责人和最后验证日期，关键文档要有验证步骤或来源代码。

## 二、目标目录

目标结构如下（概念树）。未使用的目录不提前创建；目录首次有文档时再建立它的 `README.md`。

```text
docs/
├── README.md                         # 总入口，只做导航
├── 文档目录规划.md                    # 本契约
│
├── 架构/                              # 系统边界、领域模型、运行拓扑
│   ├── README.md
│   └── 演进/                          # 已批准但尚未成为当前基线的演进方案
│       └── README.md
│
├── 协议/                              # 跨模块或跨服务的稳定契约
│   ├── README.md
│   └── 版本/                          # 只有存在多个并行大版本时使用
│       └── README.md
│
├── 功能/                              # 面向用户的功能行为和使用说明
│   ├── README.md
│   └── <业务模块>/                    # 文件、项目、任务、身份等
│       └── README.md
│
├── 集成/                              # 外部服务的接入、配置和边界
│   ├── README.md
│   └── <外部服务>/                    # Node、智能体、钱包、OnlyOffice、S3 等
│       └── README.md
│
├── 运维/                              # 部署、升级、迁移、备份、故障处理
│   ├── README.md
│   └── <主题>/                        # 发布、存储、OnlyOffice 等
│       └── README.md
│
├── 开发/                              # 本地开发、调试和生成式参考资料
│   ├── README.md
│   └── 生成/                          # 工具生成，禁止手工修改
│       └── README.md
│
├── 决策记录/                          # 已完成取舍的 ADR，不是方案草稿
│   ├── README.md
│   └── 年份/
│       └── README.md
│
├── 提案/                              # 尚未批准或尚未落地的方案
│   └── README.md
│
└── 历史归档/                          # 被替代、废弃或仅供背景参考的内容
    ├── README.md
    └── 年份/
        └── README.md
```

### 目录边界

| 目录 | 核心问题 | 放入 | 不放入 |
| --- | --- | --- | --- |
| `架构/` | 系统如何分层、边界在哪里 | 当前拓扑、领域模型、职责边界 | 具体接口字段、部署命令 |
| `协议/` | 参与方按什么契约协作 | API、事件、存储、鉴权、版本兼容 | 单纯的用户操作步骤 |
| `功能/` | 用户能做什么、系统如何响应 | 页面流程、权限表现、功能行为 | 只服务于开发者的内部实现 |
| `集成/` | Project 如何接入外部服务 | 地址、凭证、回调、依赖和边界 | 生产发布的完整 runbook |
| `运维/` | 生产如何执行和恢复 | 前置检查、执行、验证、回滚、故障 | 长篇架构论证 |
| `开发/` | 开发者如何运行、调试和查问题 | 本地调试、脚本、映射、生成物 | 当前产品功能说明 |
| `决策记录/` | 为什么做出这个重要选择 | 已批准决策及替代方案 | 尚未确认的设计 |
| `提案/` | 未来准备怎么做 | 设计草案、待评审方案 | 生产现状和已批准结论 |
| `历史归档/` | 过去发生过什么 | 被替代方案、旧架构、废弃兼容层 | 当前实现依据 |

判断边界时以“读者要解决的主要问题”为准，而不是以文档提到的技术名词为准。比如 OnlyOffice 的用户行为放在 `功能/`，接入参数放在 `集成/`，生产部署放在 `运维/`，调用字段才放在 `协议/`。

## 四、文档生命周期

每份非生成式文档都必须声明状态。新文档使用位于标题之前的 YAML front matter，存量文档在下一次实质修改时补齐。

```yaml
---
状态: 当前有效
负责人: 项目维护组
最后验证: 2026-09-14
适用版本: main
---
```

允许的状态只有：

- `当前有效`：可以作为开发、配置、部署或排障依据。
- `设计草案`：尚未批准，只能放在 `提案/`。
- `已批准方案`：已经批准但尚未成为当前基线，放在 `架构/演进/` 或对应主题目录，并明确预计落地条件。
- `已废弃`：不再使用，正文必须链接替代文档。
- `历史文档`：只提供背景，放在 `历史归档/`，不得出现在“当前推荐”索引中。

状态转换必须可追溯：

```text
提案/设计草案 -> 决策记录/已批准 -> 架构/演进/已批准方案 -> 架构|协议|功能|集成|运维/当前有效
当前有效 -> 已废弃或历史归档/历史文档
```

决策记录写“为什么选它”；当前文档写“现在怎么做”。两者不能用一篇不断追加的长文替代。

## 五、命名和内容契约

### 命名

- 文件名和目录名优先使用简体中文；`S3`、`OnlyOffice`、`Node`、`API`、命令名和协议版本等专有标识可保留英文。
- 版本统一写成小写 `v1`、`v2`，不混用 `V1`、`版本1` 和“最终版”。
- 操作文档使用“主题+手册.md”，迁移文档使用“主题+迁移手册.md”。
- 不使用“新方案”“临时”“整理版”“最终版”等无法长期维护的名称。
- 同一主题只有一个当前有效入口；不同大版本并行时才使用 `协议/版本/` 或明确的版本文件。

### 当前说明最小结构

```markdown
---
状态: 当前有效
负责人: 项目维护组
最后验证: YYYY-MM-DD
适用版本: main
---

# 标题

## 目的和范围
## 当前实现
## 配置、接口或操作
## 验证
## 故障处理或限制
## 变更记录
```

### 运维手册最小结构

```markdown
## 适用范围
## 风险和影响
## 前置检查
## 执行步骤
## 验证清单
## 回滚或恢复
## 常见故障
```

### 协议文档最小要求

协议必须写清版本、参与方、请求与响应、错误码、鉴权边界、幂等性、超时/重试、兼容策略和升级步骤。不兼容变更新建大版本；兼容性补充在原版本中追加变更记录。

### 生成式文档

生成文件必须在文件头声明：

```markdown
> 生成文件：是，请勿手工修改。
> 生成命令：npm run events:map
> 来源脚本：scripts/gen-events-map.mjs
```

生成脚本、输出路径和引用它的检索地图必须在同一个变更中更新。生成文件只记录代码事实，不在其中添加人工结论。

## 六、索引、链接和单一事实来源

- `docs/README.md` 是唯一总索引；每个实际使用的顶层目录有自己的 `README.md`。
- 新增、移动、废弃文档必须同时更新所属目录索引和根索引。
- 索引条目写清“解决什么问题”和文档状态，不只列文件名。
- 当前文档之间使用相对链接；历史文档必须链接当前替代文档；提案必须链接对应决策记录（若已有）。
- 不复制同一段协议、配置表或操作步骤。需要复用时引用权威文档并说明差异。
- 代码注释、脚本帮助和 API 生成映射是代码事实；`docs/` 负责解释边界、原因和操作方式，不能把生成结果手工维护成第二份事实。

## 七、代码变更时的同步规则

提交代码前按以下清单判断：

1. API、事件、配置、存储路径、错误码或权限改变：更新对应 `协议/`、`集成/` 或 `功能/` 文档。
2. 生产命令、环境变量、容器、Nginx、迁移或回滚改变：更新 `运维/` 文档，并补验证步骤。
3. 系统边界、领域职责或技术路线改变：更新 `架构/`，必要时新增 `决策记录/`。
4. 用户可见菜单、按钮、流程、字段、权限或错误提示改变：同一提交检查并同步 `resources/ai-kb/`，遵守其 `_schema/` 和 `feature-map.yaml` 规则。
5. 生成脚本或代码扫描范围改变：重新生成 `开发/生成/` 下的文件，并更新生成头部。

纯拼写修正、链接修正和目录迁移不需要更新 AI 知识库，但必须更新索引。

## 八、评审和持续维护

文档变更和代码变更使用同一 Pull Request；评审至少检查：

- 链接是否有效，索引是否覆盖新增或移动文件。
- 状态、负责人、最后验证日期是否准确。
- 文档描述的配置、命令、路由、错误码是否能在代码或部署环境找到来源。
- 当前文档是否错误引用提案或历史文档。
- 是否产生了重复正文或第二个“权威版本”。
- 是否需要同步 `resources/ai-kb/`。

每次版本发布或生产升级后，至少复核部署、存储、集成和当前协议文档。连续两个版本未验证且无负责人确认的文档，应标记为待复核，不得继续标为“当前有效”。

当文档目录达到以下任一条件时，必须拆分子目录并补局部 README：同一目录超过 8 篇文档、存在 3 个以上稳定主题、或索引已经需要按读者角色分组。没有达到条件时不要预先创建层级。

## 九、迁移执行顺序

迁移采用小批次、可回滚的方式：

1. 先更新根 `README.md` 和本规划，冻结新文件的落位规则。
2. 迁移一个主题的当前文档，修复引用、索引和脚本路径后再处理下一个主题。
3. 对 V1/V2/V3 文档逐篇判断：当前基线进入 `架构/`，未来方案进入 `架构/演进/`，被替代内容进入 `历史归档/`。
4. 迁移完成后删除旧位置的正文；如需兼容外部链接，只保留一页跳转说明，并标注替代路径。
5. 最后处理历史归档和生成式文档，避免先移动导致开发工具或历史链接失效。

迁移本身不改变业务行为。任何同时改变协议、配置或生产流程的内容，必须拆出独立的代码/运维变更并按第七节同步。

## 十、当前执行结论

第三节列出的存量文档已经完成迁移，根目录只保留总索引和本规划。后续维护执行以下规则：

- 新文档按第二节目标目录创建；目录首次使用时补 `README.md`。
- 新文档必须带状态、负责人和最后验证日期。
- 已迁移文件按第三节目标路径维护，不创建重复副本或移回根目录。
- `docs/README.md` 和各级 `README.md` 作为入口，新增、移动或废弃文档时同步更新。
- 生成式文档的路径由生成脚本维护；脚本路径变化时同步更新代码检索地图。
- 涉及用户可见行为的文档变更，提交前检查 AI 知识库同步。

当前目录已经具备稳定的分类、状态边界和索引入口。后续迭代应以增量维护为主，避免再次形成根目录堆积、重复正文或多份方案并存。
