# 项目管理架构 V2

本文档沉淀项目管理域的多实例集群演进方向，不代表能力已经实现。当前生产基线见 [项目管理架构](../项目管理架构.md)。

## 1. 目标与非目标

目标是支持多个无状态 Project HTTP 节点、多个 WebSocket 节点、可恢复的上传和可靠的异步作业，并支持滚动发布和故障摘除。

V2 不重写项目、任务、权限、讨论和文件模型；继续使用 MySQL 作为业务事实源、Redis 作为共享短期状态与协调设施、Warehouse S3 作为持久对象存储。跨地域多活和全局强一致事务不属于 V2 范围。

## 2. V1 的集群阻塞点

### 2.1 WebSocket FD 与在线状态

当前 `WebSocketService` 使用 Swoole `fd` 写入 `web_sockets`，并通过 `whereFd($fd)` 查询和删除。FD 只对创建它的 LaravelS 实例有效，多个实例可能重复，任何节点也不能向其他节点的 FD 执行 `push()`。

`OnlineData` 使用本机 Swoole Table 保存在线计数。用户连接在节点 A 时，节点 B 无法看到相同计数，会造成上下线事件、离线消息重试和最后在线时间不一致。

### 2.2 本机 Swoole Task 与定时任务

`Task::deliver()` 只投递当前实例的 Task Worker。若多个节点都运行相同扫描、提醒、清理、归档或 AI 任务，会产生重复执行。当前 LaravelS Timer 也不应在未改造前同时由多个节点启用。

### 2.3 节点本地上传分片

上传分片位于 `public/uploads/tmp/chunks/{userid}/{upload_id}/`。同一 `upload_id` 被负载均衡到不同节点时，合并节点无法看到其他节点分片。Office、图片和压缩临时文件同样不能由另一节点接续。

### 2.4 运行目录不是集群共享状态

`LOCAL_STORAGE_DIR` 用于指定 Laravel `storage/` 的实际目录，避免版本切换时删除其中的本地文件。V2 中如果各节点使用本地文件状态，应配置各自的稳定目录，例如 `/var/lib/project/storage/node-a`；不要将共享 POSIX 临时目录作为连接、上传或作业协调方案。

## 3. 目标拓扑

```text
Browser / Skill -> Nginx / Load Balancer
                       |
             +---------+---------+
             |                   |
             v                   v
      Project node-a       Project node-b
      LaravelS/WebSocket   LaravelS/WebSocket
             |                   |
             +--------+----------+
                      v
        Redis: session/cache/lock/presence/event bus
                      |
        +-------------+-------------+
        v             v             v
      MySQL      Warehouse S3   Manticore / Agent
```

节点必须使用一致的 `APP_KEY`、Redis prefix、数据库、Warehouse bucket/prefix、访问令牌配置与应用版本。负载均衡需要支持 WebSocket Upgrade、健康检查、连接 draining 和节点摘除。

## 4. WebSocket、在线状态与推送

### 4.1 全局连接注册

以全局 `connection_id` 替代仅使用 FD 的连接事实：

```text
connection_id = UUID
node_id       = 稳定节点标识
fd            = 仅节点内部使用
userid/platform
expires_at    = 心跳 TTL
```

Redis 保存按连接、用户和节点索引的短期信息。节点崩溃由 TTL 和节点心跳清理，不依赖 `onClose()`；MySQL 如需审计，只保留非实时派送数据。

### 4.2 跨节点路由

业务事务提交后，先解析接收用户和其连接所在的 `node_id`，按节点发布 Redis Pub/Sub、Redis Stream 或等价消息总线事件。每个 WebSocket 节点只消费自己的 channel，只向本机 FD 推送。瞬时在线推送可先用 Redis Pub/Sub，现有离线消息/通知记录继续作为可靠补偿；需要确认、重放或强顺序时再升级为 Stream 或专用消息队列。

在线状态迁移为 Redis 原子计数或用户连接集合：第一个连接上线、最后一个连接下线，同一用户跨设备和跨节点只发生一次状态转换。

Node Pusher 可以作为跨应用事件总线和统一通知出口参与 V2，但不直接取代 Project 内部 WebSocket 路由。V2 的 Project 内部在线同步仍需要解决连接归属、节点路由和本机 FD 推送；Node Pusher 更适合承接跨应用订阅、持久化回放、通知中心、Webhook/Email 和后续 Web Push。接入时应避免同一用户可见事件在 Project WebSocket、Node 通知中心、邮件和移动推送之间重复生成未读。

## 5. HTTP、作业和上传

### 5.1 HTTP 与写入

多节点 HTTP 必须强制 Redis session、cache 和 lock，禁止 file session、file cache 和节点本地锁。任务更新继续使用 MySQL 事务、唯一约束和 `lockForUpdate()`；外部 Skill、Webhook、提醒和 AI 触发入口逐步补充幂等键或明确的业务去重规则。

### 5.2 异步与调度

| 类别 | V2 策略 |
|---|---|
| 必须同步完成的校验与事实写入 | HTTP 请求与数据库事务中完成 |
| 必须可靠的通知、AI、索引和补偿 | 共享队列或持久化 worker，可横向扩展 |
| 定时清理、提醒、归档和扫描 | 独立 Scheduler/Leader，或 Redis 锁加幂等作业 |

可靠事件应在事务提交后投递；后续可采用 outbox 或等价机制，避免写入成功但异步事件丢失。

### 5.3 上传目标方案

最终将分片与上传会话放入 Warehouse S3 staging prefix：

```text
uploads/staging/{upload_id}/{part_number}
```

上传会话、分片大小、校验和、状态和过期时间写入 MySQL 或 Redis。完成操作必须幂等，最终对象只能提交一次，staging 对象按 TTL 清理。过渡期可对 `upload_id` 使用粘性路由，但节点故障仍会导致重试，因此不作为最终方案。

动态缩略图、Office 转换和压缩下载可继续使用节点本地运行目录，因为它们是可重试的一次性工作。

## 6. 实施阶段

### Phase 0：准备与观测

- 引入稳定唯一的 `PROJECT_NODE_ID`。
- 采集节点健康、连接数与 TTL、跨节点推送结果、上传会话和重复作业指标。
- 梳理 `Task::deliver()` 与定时入口，标明可靠性、幂等键和唯一执行者。

### Phase 1：共享 HTTP 基础

- 强制 Redis session/cache/lock，验证所有节点配置一致。
- 每节点按需配置稳定的 `LOCAL_STORAGE_DIR`，支持滚动发布。
- 增加负载均衡健康检查和 connection draining。
- 在两节点验证项目读取、任务更新、AK/SK 和 S3 附件访问。

### Phase 2：分布式 WebSocket

- 新增 `connection_id`、`node_id`、Redis 注册和 TTL 心跳。
- 将在线状态从 Swoole Table 迁移到 Redis。
- 建立按节点路由的推送总线，迁移 `PushTask` 在线推送路径。
- 灰度双写和比对后，删除基于全局 FD 的连接查询/删除语义。

### Phase 3：可靠异步与调度

- 可靠异步工作迁移到共享队列/worker。
- 调度收敛为单 Scheduler 或分布式锁下的幂等作业。
- 建立事务后事件投递与补偿能力。

### Phase 4：无状态上传

- 落地 S3 staging 分片、会话、校验和和幂等完成协议。
- 移除对本地 `uploads/tmp/chunks` 的跨请求依赖。
- 取消上传粘性会话要求，演练节点切换和故障恢复。

### Phase 5：正式集群

- 灰度、容量压测、节点故障、网络闪断和滚动升级演练。
- 覆盖项目讨论、任务更新、附件上传、在线状态、提醒、AI 任务和访问令牌的端到端验证。

## 7. 验收条件

1. 任意节点产生的任务、项目和讨论事件只推送到正确连接，不受 FD 重复影响。
2. 节点异常后连接在 TTL 范围内清理，用户重连不留下错误在线状态。
3. 同一任务经不同节点并发更新时，权限、排序、日志和状态保持一致；重复请求有幂等或明确冲突结果。
4. 同一上传会话的分片可被不同节点接收，最终对象校验和正确且只提交一次。
5. 清理、提醒、归档、AI 分析和通知不会在集群中无控制重复执行。
6. 任一节点滚动重启时，已提交业务数据和 S3 对象不丢失，WebSocket 客户端可重连。
7. 网页与 AK/SK Skill 仍复用同一套项目权限、任务可见性和审计规则。

## 8. 兼容与回滚

- 连接、在线状态和上传会话均先扩展 schema 与双写，再切读，最后删除旧路径。
- 在完成 Phase 2 前，生产保持单 WebSocket 节点，即使 HTTP 已扩为多节点。
- 在完成 Phase 4 前，上传故障允许用户重试，但不承诺跨节点续传。
- 每个阶段必须可关闭新路由/新消费者并回退到 V1 单实例路径，不能通过删除旧业务事实表完成切换。
