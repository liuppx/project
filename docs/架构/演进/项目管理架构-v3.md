# 项目管理架构 V3

本文档是 Project 面向社区跨项目文档协作的规划，当前不代表相关能力已经全部实现。

本文档定义如何通过 Codex 的 `project-collaboration` skill，将 `books/yeying` 中维护的社区文档发布到 Project 文件柜，供不能访问代码仓库的社区成员阅读和协作。社区文档的信息来源是 `/Users/liuxin2/Workspace/opensource` 下相关项目的当前源代码和 `docs/`，但同步器只发布整理后的社区文档，不直接公开各项目源码和内部文档。

## 1. 目标与边界

### 1.1 目标

- Codex 可以读取各项目源码和 `docs/` 作为事实依据，更新 `books/yeying` 中的社区文档，并在 Project 文件柜创建或更新公开副本。
- 同步操作复用 Project 文件柜的标准 API 和用户权限，不绕过业务接口访问数据库或存储。
- 同步是幂等的：重复执行不会创建重复文档，也不会覆盖错误的目标文件。
- 文档在 Project 中保留目录结构、源文件路径、源仓库和同步时间等元数据。
- 先支持人工触发和 Codex skill 操作，再扩展为 CI 自动同步。

### 1.2 非目标

- 第一阶段不实现 Project 与 Git 仓库双向同步。
- 不把 Project 文件柜当作 Git 分支、Pull Request 或代码审阅系统。
- 不让模型直接执行任意写操作；所有写入必须经过明确的文件柜命令和权限校验。
- 不同步包含 AK、SK、私钥、密码、生产令牌或其他敏感信息的文件。

## 2. 总体流程

```text
各项目源码 / docs
        |
        v
books/yeying 社区文档
        |
        v
Codex + project-collaboration skill
        |
        | file-lists / file-search / file-add / file-save / file-read
        v
Project 文件柜
        |
        v
Project 成员或游客分享链接
```

第一阶段采用单向发布：Git 仓库是编辑源，Project 文件柜是共享阅读和受控维护副本。同步完成后，Codex 应返回目标文件 ID、文件柜路径和验证结果。

## 3. Skill 操作契约

Codex 使用 `project-collaboration` skill 提供的标准命令：

| 操作 | 命令 | 用途 |
|---|---|---|
| 查目录 | `file-lists --pid N` | 确认目标目录和现有文件 |
| 按名称搜索 | `file-search --key KEY` | 查找已有目标，避免重复创建 |
| 建目录 | `file-add --type folder` | 建立项目和文档分类目录 |
| 建文档 | `file-add --type document` | 创建 Markdown 文档容器 |
| 写文档 | `file-save --id N --content-file PATH` | 保存 Markdown 内容 |
| 读文档 | `file-read --id N` | 回读并验证内容 |
| 上传附件 | `file-upload --pid N --file PATH` | 上传图片、PDF 等非 Markdown 文件 |
| 生成链接 | `file-link --id N --guest-access yes/no` | 设置成员外访问 |

所有命令使用 AK/SK 签名。凭证只从环境变量、配置文件或本机密钥链读取，不写入仓库、日志和聊天消息。

## 4. 目录和映射

建议为社区文档建立一个由专用 Project 账号拥有的根目录：

```text
夜莺社区文档/
├── 社区基线/
├── Chat/
├── Node/
├── Project/
├── Router/
├── Wallet/
├── Warehouse/
└── 安全与登录/
```

同步器需要维护源文件到目标文件的稳定映射。第一阶段可使用本地清单文件（不含凭证）：

```json
{
  "source": "yeying/社区产品架构.md",
  "target_pid": 123,
  "target_file_id": 456,
  "source_sha256": "...",
  "synced_at": "2026-08-21T00:00:00Z"
}
```

清单应放在未提交的本地状态目录，或作为 CI 的构建产物；不能把不同环境的文件 ID 写死在公共文档中。

## 5. 创建与更新算法

### 5.1 创建

1. 校验源文件路径位于允许的文档目录内，扩展名为 `.md` 或明确允许的附件类型。
2. 扫描内容中的敏感字段和禁止发布路径。
3. 使用 `file-lists` 确认目标父目录。
4. 使用 `file-search` 按规范化文件名查找目标。
5. 找不到目标时使用 `file-add --type document` 创建文档。
6. 使用 `file-save` 写入 Markdown 内容。
7. 使用 `file-read` 回读，校验标题和内容摘要。
8. 必要时用 `file-link` 生成只读或游客链接。

### 5.2 更新

1. 优先使用映射清单中的 `target_file_id`。
2. 回读目标文档，检查其是否仍属于预期目录和名称。
3. 若目标文档由人工修改且目标内容与上次同步基线不同，默认停止并报告冲突，不直接覆盖。
4. 无冲突时调用 `file-save` 更新内容。
5. 回读并记录新的源哈希、目标 ID 和同步时间。

### 5.3 幂等与重试

- 创建前必须搜索，不能仅按名称直接创建。
- 写入失败可以重试；创建成功但响应丢失时，重试必须通过搜索或映射恢复目标 ID。
- 每次写入后必须回读验证，不能只依据 `file-save` 成功响应宣称同步完成。
- 删除和移动不属于第一阶段自动同步动作，必须人工确认。

## 6. 权限和安全

- 使用专用文档所有者账号，避免个人账号离职导致文档失管。
- 普通社区成员使用 Project 用户级只读共享；维护者才授予读写权限。
- 安全、登录、令牌和钱包设计文档默认关闭游客访问。
- 产品介绍和稳定架构基线可以单独生成游客链接，但必须经过发布确认。
- 同步前拒绝包含 `AK`、`SK`、`APP_KEY`、私钥、密码、Cookie、生产 URL 凭证等内容。
- API 返回的链接、文件 ID 和错误信息可以写入同步日志；签名、令牌和请求头不得写入日志。

## 7. 冲突和版本策略

Project 的 `FileContent` 提供历史快照和恢复能力，但第一阶段不依赖其完成 Git 式审阅。同步记录至少包含：

- 源仓库和相对路径。
- 源 commit 或 SHA-256。
- Project 文件 ID 和父目录 ID。
- 同步时间、执行者和结果。

Git 仓库仍是唯一编辑源。Project 中出现人工编辑时，Codex 必须报告冲突并等待明确指令；不能静默覆盖。

## 8. 验证计划

第一阶段上线前必须完成以下验证：

1. 用创建时勾选“文件柜”权限范围的 AK/SK 创建测试目录和测试文档。
2. 回读文档，确认 Markdown 标题、列表、链接和中文内容未损坏。
3. 重复执行同步，确认不会创建重复文件。
4. 修改本地文档后再次同步，确认目标内容更新且历史版本增加。
5. 撤销或降低共享权限后，用另一 Project 用户验证访问结果。
6. 生成游客链接，用未登录浏览器验证公开文档；对敏感文档确认链接不可访问。
7. 使用未勾选“文件柜”权限范围的令牌验证操作失败且不泄露凭证。

当前环境若返回“访问令牌无权调用此接口”，应先确认自动化令牌创建时已勾选“文件柜”权限范围，再进行功能验收；不能用浏览器 Cookie 或其他用户凭证绕过权限。

## 9. 后续实现阶段

### Phase 1：Codex skill 人工驱动

- 使用现有 `project-collaboration` skill 命令完成目录、文档创建和更新。
- 建立本地映射清单和敏感信息扫描规则。
- 完成上述创建、更新、回读和权限验证。

### Phase 2：仓库内同步工具

- 在 `scripts/` 增加同步命令，读取映射配置并调用同一套 API。
- 支持 `--check`、`--plan`、`--apply` 三种模式。
- 默认只生成计划，`--apply` 才允许写入。
- 输出机器可读的同步结果，供 Codex 和 CI 使用。

### Phase 3：CI 单向发布

- 主分支合并后触发文档同步。
- 使用专用 Project 自动化令牌和最小权限配置。
- 将源 commit、目标文件 ID 和失败原因写入 CI 工件。
- 同步失败只阻断文档发布，不影响代码构建和部署。

## 10. 验收结论

当 Phase 1 的创建、更新、回读、重复执行、权限和游客访问验证全部通过后，才认为“本地代码和 docs 可通过 Codex skill 发布到 Project 文件柜”成立。此结论不代表已经实现 Git 双向同步、差异审阅或自动 CI 发布。
