# 项目管理架构 V1

本文档基于当前 `main` 分支代码建立 Project 项目管理域的架构基线。它只描述已经实现的边界和运行方式；多实例集群是后续 V2 方向，见 [项目管理架构 v2](./演进/项目管理架构-v2.md)。

## 1. 定位与职责

Project 是 YeYing 的项目、任务、文件协作和团队工作流业务系统。它拥有项目权限、任务状态、讨论上下文和业务审计；不负责智能体安装、模型编排或社区发布目录。Project 与 Agent Runtime 的职责边界见 [应用运行时职责边界](./应用运行时职责边界.md)。

项目管理域负责：

- 项目、成员、负责人、项目权限和邀请。
- 看板列、工作流状态、任务、子任务、标签、优先级、计划时间和循环任务。
- 任务负责人、任务可见性、任务关联、模板、项目动态和状态变更记录。
- 任务富文本、附件、任务讨论和通知。
- 供网页与 AK/SK 访问令牌共同使用的项目 API。

账号、组织、部门、通用聊天协议、文件中心、对象存储和 Agent Runtime 属于相邻领域；项目管理域只通过模型、服务和内部 API 与它们协作。

## 2. 当前运行拓扑

```text
Browser / Project Collaboration Skill
              |
              | HTTPS，登录态 Token 或 AK/SK 签名
              v
Nginx -> LaravelS / Swoole（单个 Project 实例）
              |
              +-- 项目 API、领域模型、Observer、Swoole Task
              +-- MySQL：项目、任务、成员、日志、讨论索引
              +-- Redis：session、cache、锁、短期状态
              +-- Manticore：搜索，可降级到 MySQL
              +-- Warehouse S3：持久附件、内容和图片
              +-- Agent Runtime：已安装能力的内部调用
              +-- WebSocket：当前 LaravelS 实例持有浏览器连接
```

生产使用 PHP 8.4、Laravel 13 和 LaravelS/Swoole。默认环境模板将 cache、session 和 queue 指向 Redis；MySQL、Redis、Manticore、Warehouse 和 Agent Runtime 均是 Project 外部依赖，部署边界见 [部署手册](../运维/发布/部署手册.md)。

## 3. 入口与分层

### 3.1 HTTP API

项目 API 在 [routes/web.php](../../routes/web.php) 使用动态路由注册：

```text
/api/project/{method}
/api/project/{method}/{action}
```

入口为 [ProjectController](../../app/Http/Controllers/Api/ProjectController.php)。例如 `task/one` 映射到 `task__one()`，`task/update` 映射到 `task__update()`；完整映射由 [routes/api-map.md](../../routes/api-map.md) 生成。

`ProjectController` 是历史大控制器，已经冻结。新增项目管理能力应使用新控制器，并将跨模型编排放在 `app/Module/` 或 `app/Services/`，不再继续增加该控制器方法。

### 3.2 Web 前端

Vue 2 项目工作区位于 `resources/assets/js/pages/manage/`。`ProjectPanel.vue` 是项目、看板、任务和详情的主要容器；组件经 `store.dispatch("call", params)` 调用 API，经 mitt 协调面板、邀请和任务详情。现有事件收发索引见 [前端事件总线映射](../开发/生成/前端事件总线映射.md)。

### 3.3 业务与异步

模型负责数据访问、关系和自身状态；任务变更后的日志、成员同步、通知和 AI 触发由模型、Observer、`app/Module/` 与 `app/Tasks/` 组合完成。`Task::deliver()` 投递到当前 LaravelS 的 Swoole Task Worker，不是跨节点队列。

## 4. 核心数据模型

| 领域 | 主模型 / 表 | 职责 |
|---|---|---|
| 项目 | `Project` / `projects` | 名称、说明、创建人、归档策略、AI 设置、项目讨论 `dialog_id` |
| 项目成员 | `ProjectUser` / `project_users` | 项目成员、置顶、排序与负责人角色 |
| 项目权限 | `ProjectPermission` / `project_permissions` | 项目级细粒度操作权限 |
| 看板与工作流 | `ProjectColumn`、`ProjectFlow`、`ProjectFlowItem` | 看板列、工作流及状态项 |
| 任务 | `ProjectTask` / `project_tasks` | 层级、列、状态、时间、完成/归档、可见性、优先级、循环与排序 |
| 任务成员和可见性 | `ProjectTaskUser`、`ProjectTaskVisibilityUser` | 负责人/参与人和指定成员可见名单 |
| 内容和附件 | `ProjectTaskContent`、`ProjectTaskFile` | 富文本/在线文档内容和文件中心附件关联 |
| 分类与关系 | `ProjectTag`、`ProjectTaskTag`、`ProjectTaskRelation` | 标签和任务间有向关系 |
| 模板与事件 | `ProjectTaskTemplate`、`ProjectTaskAiEvent` | 模板、使用计数和 AI 事件 |
| 审计与通知 | `ProjectLog`、`ProjectTaskFlowChange`、`ProjectTaskPushLog` | 项目动态、状态变化和推送记录 |

```text
Project 1 --- N ProjectUser / ProjectColumn / ProjectTask
Project 1 --- N ProjectFlow / ProjectFlowItem
ProjectTask 1 --- N ProjectTask（parent_id，子任务）
ProjectTask 1 --- 1 ProjectTaskContent
ProjectTask 1 --- N ProjectTaskFile / ProjectTaskUser / ProjectTaskTag
ProjectTask N --- N ProjectTask（ProjectTaskRelation）
ProjectTask 1 --- 1 WebSocketDialog（dialog_id，讨论）
```

`Project` 与 `ProjectTask` 均使用软删除。归档是独立业务状态；任务可跟随项目归档。附件数、讨论消息数、子任务完成比例、今日任务和逾期状态等由任务模型追加属性计算。

## 5. 权限、可见性与工作流

`project_users.owner` 是项目角色事实源：`0` 为普通成员，`1` 为主负责人，`2` 为项目管理员。`Project::isPrimaryOwner()`、`isDeputyOwner()` 和 `isOwner()` 统一封装判断。成员变更会同步项目关联讨论的成员关系。

任务权限不是只检查项目成员关系，还必须经过：

```text
登录用户或访问令牌所属用户
  -> 项目成员与负责人关系
  -> 项目权限配置
  -> 任务 visibility、任务成员和指定可见成员
  -> 当前操作的业务规则
```

任务状态由 `column_id`、`flow_item_id`、`flow_item_name`、`complete_at`、计划时间、优先级、`loop`/`loop_at` 和 `parent_id` 等字段共同表达。并发更新使用 MySQL 事务和必要的 `lockForUpdate()`；状态变更写入 `ProjectTaskFlowChange` 和 `ProjectLog`，再触发通知、提醒或 AI 后续工作。

## 6. 讨论、动态与通知

项目与任务通过 `dialog_id` 关联通用 `WebSocketDialog`。讨论消息、回复、图片、已读状态和传输协议由聊天领域维护；项目域负责创建关联、同步参与人，并在任务详情中聚合讨论。任务附件由 `ProjectTaskFile` 关联文件中心，与讨论消息里的图片不是同一数据模型。

领域动作会投递 `PushTask` 等本机 Swoole Task，Task Worker 查询连接并调用当前实例的 WebSocket Server 推送。离线消息、通知日志、邮件和移动端通知依赖其各自的持久化记录或外部服务兜底。

Node Pusher 是可选的跨应用事件桥，不是 V1 内部实时同步的前置依赖。任务变更、看板刷新、文件变更和讨论消息仍以 Project 自带 WebSocket 为准；配置 `PUSHER_APP_*` 只表示 Project 具备向 Node Pusher 发布事件的服务端凭据。需要外部应用订阅、统一通知中心、事件持久化回放、Webhook/Email 投递或跨实例 fanout 时，再选择少量关键业务事件调用 Node Pusher publish client。

验证 Node Pusher 配置时使用：

```bash
php artisan pusher:smoke --channel=public-project-smoke --type=project.smoke --persist=1
```

命令返回 `accepted=true` 只能证明凭据和 Node publish API 可用；真实业务是否生效，还要看具体业务动作是否调用 publish、是否带 `notification` / `persist=true`，以及前端或外部订阅方是否监听对应 channel。

## 7. 文件与内容存储

持久化文件统一经 `PersistentStorage`：

- `FILE_STORAGE_DISK=local` 时，`public/uploads/` 是最终对象源。
- `FILE_STORAGE_DISK=s3` 时，Warehouse S3 是唯一事实源；Project 对 `/uploads/...` 签发短时效 URL，浏览器直连对象存储。
- 任务内容、任务附件、讨论图片、头像、报告附件和桌面发布物均使用该存储边界。
- `public/uploads/tmp/`、`storage/app/tmp/`、`storage/temp/` 是可丢弃的本地工作目录。

详细规则见 [文件内容存储 v1](../协议/文件内容存储协议-v1.md) 和 [持久化存储协议 v1](../协议/持久化存储协议-v1.md)。

## 8. 标准 API 与访问令牌

网页和机器协作不维护两套项目业务 API。AK/SK 请求经访问令牌验签后，以令牌所属用户身份进入相同控制器、项目权限、任务可见性和审计规则。令牌由 `AutomationToken`、项目范围和 `AutomationTokenAudit` 审计组成，只能访问已授权项目与 scope 内的标准 API。

因此 `project-collaboration` Skill 是标准 API 客户端，而不是机器人专用业务后端。完整协议见 [访问令牌协议 v1](../协议/访问令牌协议-v1.md)。

## 9. 单实例部署基线

V1 的生产基线是一个对外 LaravelS/WebSocket 实例，内部可有多个 Swoole worker 与 task worker，并共享 MySQL、Redis、Manticore、Warehouse S3 和 Agent Runtime。

- `LOCAL_STORAGE_DIR` 可指定 Laravel `storage/` 的实际目录；留空时使用当前 release 内的 `storage/`。

V1 不承诺多 LaravelS 实例负载均衡、跨节点 WebSocket 推送或跨节点分片上传。原因和演进路线见 V2。

## 10. V1 不变量

1. 项目、任务、权限、讨论关联和审计记录以 MySQL 为业务事实源。
2. 机器访问复用标准 API 和用户权限，不维护机器人专用业务 API。
3. S3 模式下持久对象只以 Warehouse 为事实源，不保留永久本地兼容副本。
4. 临时目录可清理，但不能把在途上传、Office 保存、图片处理或打包下载误判为已提交业务数据。
5. 项目讨论继续复用聊天领域，项目域不复制消息存储或绕过聊天权限。
6. 新增项目管理编排不继续扩大 `ProjectController`。
