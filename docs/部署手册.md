# 部署手册

本文档说明 YeYing Project 的生产部署、运维和升级流程。生产环境使用生成的 `project-vVERSION-COMMIT.tar.gz` 版本包，应用直接运行在 Ubuntu 主机的 PHP 8.4 + LaravelS/Swoole 上。生产服务器不需要 Node.js。

## 1. 构建版本包

在构建机执行：

```bash
./scripts/package.sh
```

不带参数时，脚本会从 `origin` 拉取远端 tag，基于 `origin/main` 创建下一个 patch tag（例如 `v0.0.1` -> `v0.0.2`），推送 tag，然后打包该精确提交。如果最新 tag 已经指向 `origin/main`，则跳过打包。

如果要打包已有 tag，不创建新版本号，可以显式指定：

```bash
./scripts/package.sh v0.0.2
```

如需从其他 remote 打包，可设置：

```bash
PACKAGE_REMOTE=upstream ./scripts/package.sh
```

脚本会在临时 Git worktree 中安装前端依赖、构建静态资源、安装生产 Composer 依赖，并将版本包写入 `output/`。版本包会排除 `.env`、`node_modules`、`package-lock.json`、Git 历史和运行日志。

## 2. 安装 Ubuntu 依赖

解压版本包后，在生产服务器执行：

```bash
sudo ./scripts/ubuntu-deps.sh --install
./scripts/ubuntu-deps.sh --check
```

该脚本会安装 PHP 8.4、Swoole、Composer、LDAP/GMP 等 PHP 扩展、MySQL/Redis 客户端工具，以及必要的构建和运行工具。`scripts/starter.sh` 只负责启动应用，不负责安装 PHP。

## 3. 配置和初始化

仓库只提供 `.env.template` 作为配置模板。复制为 `.env` 并填写生产环境配置：

```bash
cp .env.template .env
# 编辑 .env，填写 APP_URL、MySQL、Redis、Manticore、LaravelS 等配置
./scripts/install.sh
```

`.env` 是实际生效配置，包含密钥和环境参数，已被 Git 忽略，禁止提交。SMTP 等业务配置由管理员在 Web 控制台配置。

至少确认以下配置：

```dotenv
APP_ENV=production
APP_DEBUG=false
RUNTIME_DRIVER=yeying
LARAVELS_LISTEN_IP=127.0.0.1
LARAVELS_LISTEN_PORT=2222
```

当 LaravelS 直接运行在主机上时，`DB_HOST`、`DB_PORT`、`REDIS_HOST`、`REDIS_PORT` 必须填写主机可访问的 MySQL 和 Redis 地址。Project 不会启动 MySQL、Redis、Manticore、MinIO/S3、PlantUML Server 等通用中间件。

## 4. 启动和管理

```bash
./scripts/starter.sh start|status|restart|stop
```

日志位置：

```text
storage/logs/starter.log
storage/logs/laravel.log
```

生产环境建议使用 Caddy 或 Nginx 作为前置代理，负责 HTTPS、WebSocket 转发、上传大小限制和静态资源缓存。应用监听地址保持在 `127.0.0.1`。

## 5. 健康检查

默认命令检查 readiness；使用 `all` 检查依赖，使用 `json` 便于自动化：

```bash
./scripts/health-check.sh
./scripts/health-check.sh --level all
./scripts/health-check.sh --level all --format json
```

- `liveness`：检查 LaravelS PID，并调用 `/health`。
- `readiness`：确认 LaravelS 能正常服务应用请求。
- `dependency`：只读检查 MySQL `SELECT 1` 和 Redis `PING`。
- `all`：按顺序执行 liveness、readiness、dependency。

MySQL 和 Redis 是必需依赖。健康检查脚本不会启动、停止或修复共享中间件。可通过 `HEALTH_BASE_URL`、`HEALTH_TIMEOUT`、`HEALTH_RETRIES` 覆盖默认参数。

## 6. 管理员和密码运维

常用命令：

```bash
./cmd repassword                 # 重置管理员密码
./cmd repassword 1               # 按用户 ID 重置
./cmd repassword user@example.com # 按邮箱重置
./cmd ensure-admin               # 没有管理员时创建或修复默认管理员
./cmd help
```

`./cmd repassword` 不带参数时，只会处理 `identity` 中包含 `admin` 标记的用户。如果提示 `错误：未找到管理员用户！`，不要回退重置任意第一个用户；应先给目标账号授予管理员身份。

`./cmd repassword` 使用 `.env` 中的 MySQL 连接。本机存在 `mysql` 客户端时优先直连；如果没有，会自动使用当前 `docker-compose.yml` 的 `mysql` 服务或运行中的 `mysql` 容器。需要指定非默认容器时，可显式设置 `MYSQL_CONTAINER=容器名`。

`./scripts/install.sh` 在迁移完成后会自动执行管理员初始化。如果需要修复已有环境，可执行：

```bash
./cmd ensure-admin
```

如果已有管理员，命令只打印管理员信息，不修改密码。如果没有管理员，会创建或修复 `admin@yeying.com`，打印一次性初始密码，并要求首次登录后修改密码。

## 7. 版本化发布和数据目录

生产环境通常通过 `/opt/deploy/project` 软链指向版本目录，例如：

```text
/opt/deploy/project -> /opt/deploy/project-v0.0.4-7a61a82
```

正式上传文件应使用 S3 或其他外部持久存储，不依赖 release 目录中的 `public/uploads/`。`.env` 由部署系统注入或复制到每个新 release，安装脚本不负责跨版本保留配置。

Laravel 的 `storage/` 实际目录可由 `.env` 中的 `LOCAL_STORAGE_DIR` 指定。留空时使用当前项目的 `storage/`；生产可设置为不会随版本删除的绝对路径，例如：

```dotenv
LOCAL_STORAGE_DIR=/var/lib/project/storage
```

每个新 release 执行 `scripts/install.sh` 时，脚本会先迁移已有 `storage/` 内容，再将项目中的 `storage/` 整体链接到该目录。`run/` 与 `public/uploads/tmp/` 不受此配置控制。

生产环境应以 S3 bucket/prefix 或其他外部存储作为持久文件源。`public/uploads/tmp/` 和其他本地工作文件是可丢弃的临时文件，不能作为业务数据备份。

## 8. 升级流程

升级前先备份 MySQL、持久化上传文件和生产配置。推荐顺序：

1. 构建并上传新版本包。
2. 解压到新的版本目录。
3. 为新 release 提供 `.env`，确认外部文件存储可用；如配置了 `LOCAL_STORAGE_DIR`，执行 `scripts/install.sh` 创建 `storage/` 目录链接。
4. 执行数据库迁移和必要的数据迁移。
5. 切换 `/opt/deploy/project` 软链到新版本目录。
6. 执行 `./scripts/starter.sh restart`。
7. 执行健康检查和核心读写验证。
8. 确认稳定后清理旧版本和临时文件。

详细生产升级步骤见 [生产升级操作手册](./生产升级操作手册.md)。

## 9. S3 存储迁移

S3 迁移必须按操作手册执行，不能直接切换配置。迁移完成并验证 final delta 后，才能设置：

```dotenv
FILE_STORAGE_DISK=s3
```

详细流程见 [S3 存储迁移操作手册](./S3存储迁移操作手册.md)。
